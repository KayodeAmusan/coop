## Architecture and reuse

The application is native PHP with PDO/MySQL, server-rendered administrative pages, Tailwind styling, and separate JSON endpoints. Preserve this stack. Root pages cover employee administration, payroll periods, contributions, finance, accounting reports, and loan administration. `auth_api/api/` supplies JWT member endpoints and session-based administration. `loan/` is another loan processing subsystem; `api/` contains legacy processing and accounting endpoints. These multiple entry points must share domain rules.

Reuse `libs/services/AccountingEngine.php` for journal lifecycle after repairing exact arithmetic, atomic transitions, idempotency, and reversal behavior. Reuse `MemberAccountManager.php`, `AccountBalanceCalculator.php`, `BankReconciliationService.php`, `PeriodClosingProcessor.php`, `libs/reports/`, and existing statement/export pages after reconciliation checks. Reuse JWT/session mechanisms, `includes/member_identity_helper.php`, existing member identifiers, profile approval, notifications, and import response helpers. Avoid adding a second balance system.

Composer declares PHPMailer, dotenv, PhpSpreadsheet, and Guzzle. TCPDF is checked in under `auth_api/lib/tcpdf/`. There is no root Node manifest. The recursive tree contains no `oouth_coop_app/` Flutter source despite README claims; downloadable APKs cannot substitute for maintainable member UI source. README setup references also need verification against actual paths.

## Migration and reconciliation strategy

Take a tested backup and inventory the actual staging schema before applying additive, versioned migrations. The repository contains multiple loan setup variants, so determine which is deployed instead of importing all scripts. Snapshot member IDs, payroll IDs, account/period totals, principal/interest, share quantities, documents and consent history. Quarantine duplicate/placeholder identities and unmatched rows for staff resolution; never infer identity by name or fabricate opening balances.

Map source transaction IDs and source periods to unique migration keys. Reconcile each member and product plus aggregate control accounts; distinguish deposits/principal/liabilities/share capital from income and expenses. Use approved opening entries only where historical detail is unavailable, preserving signed reconciliation evidence and unexplained differences as explicit exceptions. Retain old IDs, effective/posting dates, actors and source references.

Backfill term versions and consent evidence honestly: historical status must not become fresh authenticated consent. Existing loans require an explicit grandfathering or re-consent policy; pending approvals must fail closed until evidence meets policy. Do not silently invalidate historical accounting or overwrite posted records.

Stage batches with dry-run totals, stable row keys, clear all-or-nothing versus partial rules, durable progress and safe retries. Copy private documents with ownership/metadata/checksums and authorize downloads before removing public access. Re-run reconciliation and restore rehearsal in staging, then arrange a separately authorized production cutover with a write freeze, final delta reconciliation and rollback plan. Preserve statements and audit history after membership closure.
