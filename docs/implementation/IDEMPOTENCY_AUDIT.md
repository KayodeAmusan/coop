# System idempotency audit

Date: 2026-10-21. Scope: static inspection of the current working checkout, including legacy PHP entry points, financial services, member administration, imports, uploads and notification jobs. Other agents are changing this checkout concurrently; this is a source inventory, not a production reachability certification or a whole-system completion claim. No production configuration/data was read or changed for this audit.

## Reading the matrix

**Good** means the named business command has a durable identity, payload conflict detection, stored outcome and transactional protection supported by focused tests. It does not certify its whole module. **Partial** means some concurrency/state protection exists but successful business-command replay is incomplete. **Missing** means no durable business-command receipt was located. **Blocked** means the entry point currently refuses the mutation. A same-ID no-op, uniqueness error, existence check, rate limit or disabled button is not a general business-command receipt.

`None found` in tests means no focused test was located during this source audit; it is not a claim that no other test exists. Financial transaction atomicity does not make an external email, push, SMS, scanner or filesystem operation atomic.

### Critical payroll replay hole

`classes/process.php::isTransactionCompleted` checks the existence of `tbl_mastertransact`, not an immutable source event or linked ledger receipt. `classes/delete.php` deletes this marker and other operational tables without reversing retained posted journals. A later process request can therefore create another journal for the same member/period. A unique journal source document must not be introduced blindly: source documents can legitimately repeat elsewhere. Repair requires an explicit payroll run/revision identity and a controlled correction workflow, not a broader uniqueness guess.

## Legacy reachability inventory

Current `classes/controller.php` is a small deductions/period router. Its `closeActivePeriod` case currently exits without closing anything. Do not confuse its view-period toggle with `PeriodClosingProcessor`.

`classes/controller_backup.php` and `classes/controller copy.php` contain a much larger dispatch surface. Their deployed reachability was **not established**; PHP files under a web root are not safely assumed dead. Mutations include user/company/cost-centre/department creation; earning/deduction/loan/union parameters; corporate loans and repayments; employee allowances and deductions; last-pay and cheque/bank updates; organization/period updates; period/staff-payslip deletion; new employee and online account creation; grade/step changes; employee changes; individual/global payroll; leave; employee suspension/deactivation; batch processing; password resets and user deactivation. No general command key/hash/result receipt was located. `classes/model.php` generic insert/delete/audit helpers do not supply one. These aliases must be explicitly routed through protected commands or denied by deployment, then tested; removing source files or assuming no traffic is not an authorized substitute.

Other aliases requiring the same inventory treatment are the Excel copy, parallel `loan/` APIs, `loan/postAccount_.php`, direct finance CRUD, both notification service trees and old credential/message scripts. Source presence identifies a review obligation; it does not prove a working endpoint, authorization, production routing or successful execution.

## Smallest dependency-ordered implementation plan

1. **Shared durable command receipt using the existing loan-product pattern.** Require authenticated scope + action + caller-stable key; unique constraint, canonical validated payload hash, original successful result, locked replay/conflict handling and same transaction/savepoint as business writes. Do authorization before reading a receipt. Keep absent/NULL optional compatibility only while enumerated legacy callers are migrated, never as evidence of coverage. Test concurrent same-key replay, changed-payload conflict, rollback, caller-owned transaction and uncertain response.
2. **Close financial bypasses first.** Integrate current deductions, direct finance CRUD, legacy loan creation/posting and destructive payroll endpoints. Replace status toggles with explicit desired state and expected version in a keyed command. Route aliases through one service or fail closed with a truthful migration message; owner must decide intentional removal of workflows.
3. **Give payroll an immutable business run identity.** Persist input/revision manifest, member outcomes, journal links and response together. A deleted operational marker must not erase posting identity. Bind corrections to an explicit original run and reversal/reprocess command. Do not auto-repost historical periods or invent revision policy.
4. **Wrap reconciliation and closing as whole commands.** Reconciliation receipt covers its record plus both adjustment journals. Closing receipt binds period, approved rules/version and results/openings. Preserve exact locks and caller transactions. Per-journal no-op is insufficient when the command creates a new journal each attempt.
5. **Make imports explicit batch commands.** Bind stable batch key to file/content digest, parser/mapping version, period and canonical rows; persist row decisions/rejects and final result. Check stale target state before apply. Retry must not silently recalculate omitted-member zeroing against a changed roster. Decide overwrite/append and corrections with owner before enabling changed semantics.
6. **Cover member/settings/reviews and remaining uploads.** Save the originally assigned member ID on creation. Use version-aware desired state for updates/reviews. Bring payslips into a private, associated, keyed lifecycle. A scan attempt needs durable identity without repeated review invalidation. Keep evidence upload/review safeguards intact.
7. **Use a transactional outbox for jobs.** Queue one message per business event in the command transaction, lease work atomically, persist attempts/provider IDs and retry policy. Provider acceptance with lost acknowledgement may remain uncertain; claim exactly-once only where the provider supplies a verified idempotency contract. Avoid holding DB transactions across network calls.
8. **Complete lower-impact coverage and prove deployment reachability.** Events, rota, settings, credentials, cancellation, cleanup and all legacy aliases still count under the owner's whole-system requirement. Add route-level inventory checks and deployment deny rules for obsolete entry points, not merely service unit tests.

## Owner decisions and remaining risks

Owner decisions are still needed for intentional repeat economic events under a new key, correction/reprocess revisions, historical/closed-period changes, import replacement semantics and receipt/evidence retention. Technical receipt retention must outlive meaningful replay risk; silently expiring financial keys can restore duplicate-write risk. A new key is not authorization to repeat an event whose domain identity is already consumed.

Reopening remains fail closed when closing/appropriation journals or later carried openings exist. Idempotency must not bypass that protection. A controlled reversal/reconciliation workflow, historical duplicate-journal review and deployment reachability audit remain unfinished. This inventory is not a claim that all mutations are protected.

Integration update: classes/delete.php now refuses deletion before any DB connection. The historical marker-deletion vulnerability described above motivated this block; other aliases/imports still need review. No broader deletion reroute was performed after automatic review rejected it.
