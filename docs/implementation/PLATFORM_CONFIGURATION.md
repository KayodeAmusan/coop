# Deployment settings and Auracle access

Each cooperative runs its own deployment and database. Apply `database/migrations/20261021_platform_configuration.sql`; it creates no login credentials and grants no cooperative user platform access.

Provision a separate Auracle operator using `php tools/provision_platform_admin.php --username=EXPLICIT_NAME`, supplying a unique password through protected standard input. Do not put passwords in command arguments, shell history or source. Existing operators require explicit `--reset`; resetting increments the authentication version and revokes existing sessions. Deploy behind HTTPS. Loopback development is the only HTTP exception. Platform sessions use a separate cookie and are bound to the deployment; ordinary cooperative Admin sessions cannot configure branding or integrations.

Set `PLATFORM_CONFIG_KEY_FILE` to an absolute private file outside application/web roots and document-upload storage. Its contents are base64 encoding of 32 cryptographically random bytes. Restrict OS permissions/Windows ACLs to the application operator and runtime account. Back up the key separately from the database. Losing it makes existing credentials unreadable. No automatic key rotation or recovery mechanism is provided; controlled decrypt/re-encrypt migration is required before changing it.

Use `platform_login.php` and `platform_settings.php`. Credentials are write-only: retain, replace or clear explicitly. Database values use authenticated AES-256-GCM encryption with provider/field binding; settings responses, command history and audit metadata contain no plaintext credentials. Stable command keys and expected revisions protect retries and concurrent settings updates. Never expose the server-only runtime helpers through an API.

SMTP testing connects, negotiates verified TLS, authenticates and quits without sending a message. Paystack testing performs its documented read-only balance request and returns only connectivity status; it does not return balances or create transactions. No real external calls were made during automated verification. References: https://paystack.com/docs/api/authentication/ and https://paystack.com/docs/api/transfer-control/#check-balance . Generic SMS configuration stores HTTPS endpoint/authentication/field mappings, but the sending adapter is explicitly not implemented. Saving it or checking readiness never reports a successful message or connection.

Branding colors/name can be saved independently. Logo JPEG/PNG and favicon PNG uploads have a measured 5 MiB bound, opaque server identifiers, signature/MIME validation and a required clean result from the configured private scanner. Configure `PRIVATE_DOCUMENT_STORAGE_ROOT` and `DOCUMENT_SCANNER_ADAPTER` as described in GUARANTOR_EVIDENCE.md. No scanner is installed by this change, and unavailable scanning blocks public branding upload. Public asset reads only serve registered clean images with verified hash/size and safe MIME/security headers. Original filenames, filesystem paths and storage keys are never public. ICO/SVG and image re-encoding are not implemented.

Integration runtime bindings in legacy email/notification callers are a separate integration checkpoint; verify those changes before claiming every workflow uses this configuration. Configuration and connection checks do not authorize real payment/message dispatch.
